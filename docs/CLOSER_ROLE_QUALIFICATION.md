# Closer role qualification

Closer routes distinguish candidate inventory, exact execution identity, role
suitability, installed transport confinement, operator caps and provider capacity.
None substitutes for another. `closer_role_qualification` is shared by the
router, dispatcher, prelaunch pool recheck and campaign selector.

The roles are `bounded_classification`, `strong_criterion_adjudication` and
`constrained_repair`. Effort remains part of the immutable execution identity;
it is not a role eligibility threshold. A qualified low-effort profile can serve
a strong role, and a high-effort profile without that role's evidence cannot.
Luna high receives no automatic senior status.

## Qualification evidence

`ROLE_QUALIFICATIONS` is a reviewed source registry, initially empty. A record
binds one qualification ID and role to the complete active profile identity:
provider, agent, requested model, effort, permission, transport, adapter version,
prompt version, capacity pools and explicit-selection policy. It includes the
identity digest, original qualification/expiry timestamps and evidence references
with SHA-256 digests. Missing, conflicting, expired, malformed, retired or changed
identities fail closed. Capacity JSON and model output cannot grant qualification.

Read-only role evidence must establish data-only operation without tools, MCP,
hooks or project context; strong-role evidence additionally names the
criterion-only scope. Runtime eligibility checks the exact installed build
against the supported confinement adapter. Currently only the existing pinned
Claude data-only adapter is supported. Registering Codex, Gemini, Cursor, Vibe or
Muse candidates does not activate a tool-free transport for them.

Repair evidence must establish mechanical-only behavior, enforced path and
operation allowlists, an isolated workspace and required tests. It cannot grant
substantive-edit or publication authority. The existing action plan and guarded
queue must separately admit every effect. The registry contains no fabricated
production qualification for these capabilities.

Selection checks current role evidence and operator caps. Invocation rechecks
the canonical active profile, retirement map, role evidence, installed transport
and current capacity while holding the existing shared provider-pool slots.
Qualification loss before invocation does not cause a provider call. Provider
or action effects already of unknown outcome retain the existing reconciliation
path; this module supplies no retry or closure authority.

Healthy capacity without an eligible role/policy is recorded as
`qualification_unavailable`, rather than reported as quota exhaustion. The
pending event retains target, revision and role for controller re-entry. Typed
hold owners, scheduling, attempt budgets and escalation consumers remain the
next implementation slice.

## Candidate inventory and Claude policy

`execution_profiles.CLOSER_CANDIDATE_MODELS` records candidate interest only.
Unknown Spark identifiers remain unset; no flags or entitlements are inferred.
Profile registration is separate from production role qualification.

The routine Claude Sonnet ceiling is removed. Opus low/high profiles use the
locally verified `claude-opus-5-5` model ID and explicit effort with the shared
Claude capacity pool. Historical Sonnet identities remain unchanged. Explicit
operator caps still constrain automatic profile selection, including Closer
routes and unprofiled command fallback. Explicit caller-named profile behavior
retains the existing contract.

## Staged activation

This source change does not install or deploy a package, create a scheduler or
change live security/closure settings. No production model is qualified by the
synthetic fixture tests. Existing installed integration duties remain in place.

Before qualified package activation, the coordinator must supply real reviewed
role evidence and complete the associated production request/repair enforcement:
named disputed criterion requests for strong adjudication, specific qualified
security/conflicting-authority owner routes, and operation-level mechanical
limits. Candidate metadata or the empty registry is not activation readiness.
No production role record should be added until those obligations have direct
test evidence. Deployment remains with the existing rollout owner.

Once qualified, initiation still uses the existing 15-minute demand controller's
`closer_campaign.controller_entry`/`tick_safe` hook. No new launcher model or
scheduler is required.
