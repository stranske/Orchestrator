# Source-upgrade isolation route

`closer_native_source_upgrade.py` is a bounded preparation/CAS boundary for a
terminal worker whose Source correction stopped before Native ACT. It accepts
the exact reviewed owner-criterion disposition, or the separately reviewed
pre-route exception-capacity disposition, and `completed=false` /
`accepted=false`. The former requires an empty ACT queue and null deferred
operation accounting. The latter requires the exact capacity-deferred result,
no ACT stage or coding continuation, a source-native interpretation with no
provider generation or selected profile, and its retained intake reference.
Both require pristine controller custody and the unchanged remote index anchor.
It does not reinterpret retirement evidence, retry the old campaign, or create
new business demand.

The supported predecessors are reviewed `f858dc3857ad7a90461126abd945edc0d380d9b3`
(owner criterion, 191 modules),
`4e8ae9de575bc1108498933fb0cd0ee495a42aa8` (pre-route capacity, 192 modules), and
`17be674425c41f619f38325c4266c5983366094f` (the reviewed pre-ACT ownership-clock
stop, 192 modules).
Each exact module map and public descriptor, plus the physical interpreter,
are pinned before any old import. The current release has a different module
closure; its strict validator is used only for the replacement. Old code is
captured into a private temporary directory, rehashed before import, and runs
its own version-aware validation against the original manifest/proof paths.
Undeclared Python or cached bytecode is refused before execution, and original
closure/manifest bytes are checked again before accepting the diagnostic.
The parent captures exact campaign bytes into the private staging directory;
the old campaign reader takes its lock on that snapshot. Cohort and proof
validation retain the original campaign path. This avoids reacquiring the
parent's real campaign lock during locked plan validation. The returned
snapshot digest must match the captured reference and the original bytes
must remain unchanged. Validate this composition under the actual plan lock
closure before another release, as well as outside the locks.
Validate this read-only boundary against the actual predecessor before a new
full release; simulated transition fixtures alone do not establish compatibility.

The 17be historical reader is further pinned to worker `59dfb3c05e55` and its
exact immutable result digest. It authenticates the original signed admission,
assignment/report pins, worker handoff, terminal B/C0 cleanup, completed round,
frontier, and scoped stop. It validates the captured qualification at the signed
admission time and at the authenticated provider receipt inside B. This permits
historical readback after that old qualification expires. It returns facts with
`completed=false` and `accepted=false`; new Runtime admission continues to require
current qualification. Original files, generic admission validators, and current
capacity policy remain intact.

Before changing the wrapper it validates immutable old state/result/cohort/round
references, runs a bounded `-I -B` hash diagnostic under the old physical
interpreter, seals the current disposition, and writes an immutable intent. The
seal, intent, and post-CAS known receipt are all signed with the current
observation-root mechanism key; for a clean current observation root,
`apply` provisions that existing mechanism-domain key only after its second
locked plan validation and before the first seal is written. Recovery never
creates or replaces it. Unsigned or substituted records are held. The seal
path is fixed beneath that current observation root. The
CAS is permitted only from the old manifest's canonical wrapper render to a
different current manifest's pinned render. After CAS, validation is against
the new contract only; invoking the old contract would be circular because its
wrapper pin intentionally no longer matches.

A complete matching pre-CAS seal can resume the same operation after a later
intent write fails, provided the old wrapper preimage, absent new state, all
source facts and the externally confirmed plan digest revalidate under the
original locks. Existing records are never overwritten. Partial or different
records remain held. After replacement, a missing known-CAS receipt remains
uncertain and cannot create a campaign or retry the CAS automatically.

The strict policy rebase may also add the static coding-worker capability
derived from the existing controller installation's sole complete Codex coding
consumer. Source validates its session admission policy, profile digest, current
budget and publication mode. Caller-selected capabilities remain refused. This
prepares the later authenticated continuation producer; it creates no coding
admission, worker or publication by itself.

Operator flow is deliberately explicit and uses the fully installed Runtime
API only: call `plan` with the old witnesses, replacement manifest, strict
rebound worker configuration/frontier, and installed release journal; call
`apply` with that exact plan confirmation; then call `prepare_held` with only
the sealed disposition and its plan digest. `prepare_held` creates one inert
generation-one HELD campaign through the readmission intent/known protocol.

That is still non-authoritative. A later, separate normal
`closer_native_readmission.admit_initialized` call must validate the current
source factory and typed demand before clearing the hold. It must not reuse old
authority or invoke old native entry.
## Manual historical-readback audit

For the reviewed 17be predecessor, run
`scripts/audit_closer_historical_readback.py` with explicit `--source` (the
Source checkout's `src` directory), `--old-manifest`, `--old-state`, and physical
`--interpreter` paths. It emits a JSON receipt for the authentic positive
diagnostic and staged-child corrupted-data refusals, including missing,
expired-at-admission, and different completion qualification records. The real
validators remain active. Original evidence hashes must remain unchanged.

This read-only local integration audit needs the retained case evidence; it is
separate from portable CI tests and grants no runtime, worker, or effect authority.

Use `--case ownership-budget` only for the separately pinned Source 8a
predecessor. The default remains the literal historical clock case. Both modes
validate their own immutable worker/result evidence and retain the existing
signature, qualification, cleanup, no-effect, custody, and wrapper-CAS gates.

The CSV canary has a separately pinned existing-delivery observation. It
authenticates its original target, assigned corrective issue, reciprocal open
delivery, native assignment and permission, and unchanged final observations.
Other references remain closed or unselected/unknown; this route can never
produce no-incumbent authority. Ordinary targets retain their original
foreign-lineage and ambiguity holds.

For the exact Source 8a predecessor, Source can project the coding consumer's
GitHub owner from the mistaken execution-agent name to the pinned native
controller principal. This changes only newly prepared metadata. The actual
assignee and PR author must still be authenticated at observation and effect
time. The old sealed manifest, admission, and consumer are never edited.
